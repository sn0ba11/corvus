# Architecture

OSINT Workbench is a local monolith for the UI/database and a set of replaceable tool runners. FastAPI serves Jinja2/HTMX pages and SSE, SQLAlchemy persists to SQLite, and an in-process asynchronous manager coordinates investigations. Redis and Celery are deliberately absent.

```text
Browser (loopback)
  -> FastAPI/Jinja2 + CSRF/auth/security headers
      -> JobManager (investigation + per-tool semaphores)
          -> fixed Adapter command array
              -> private HTTP job protocol
                  -> isolated runner: subprocess.Popen(array, shell=False)
                      -> pinned upstream executable
      -> SQLite + restrictive /data/raw paths
      -> shared presentation summary
          -> dashboard and investigation console
          -> JSON evidence and analytical HTML report
      -> investigation graph projection
          -> stable typed nodes/edges derived from SQLite evidence
          -> dependency-free local SVG canvas and provenance inspector
          -> separately persisted audited layout positions
          -> local PNG and portable graph-JSON export
      -> bounded username pivot queue
          -> explicit username fields from found/likely email evidence
          -> analyst approval or per-case automatic opt-in
          -> depth-one Maigret / Sherlock / Blackbird follow-up runs
      -> full-name search boundary
          -> in-process bounded Bing RSS adapter with relevance filtering
          -> private bundled SearXNG JSON adapter using keyless engines
          -> source-specific per-query evidence + consolidated JSON provenance
          -> allowlisted Google/Bing query generation and signed manual launch tokens
          -> reusable local templates and analyst-selected filters
          -> bounded public-result import with canonical-URL deduplication
      -> JSON / CSV / self-contained HTML export
      -> first-class location evidence register
          -> declared profile locations
          -> review / fitness / event / photo observations
          -> hardened structured public-page collector
          -> conservative place clustering and dated provenance
      -> explicit Internet Archive boundaries
          -> CDX capture discovery and bounded archived-page retrieval
          -> analyst-triggered Save Page Now submission
      -> managed-browser client
          -> token-authenticated private browser-control network
          -> persistent Playwright/Chromium profile and noVNC operator desktop
          -> named screenshot/HTML/manifest evidence volume
```

The browser agent is a standard service and the app waits for its health before starting. The app mounts browser evidence read-only and calls the agent over a dedicated internal control network; the agent is not attached to the collectors' backend network. Chromium has egress, but every HTTPS navigation must match the configured top-level allowlist, all requested network destinations are resolved and rejected if any address is non-public, and mixed-content/private-address subresources are blocked. Embedded credentials, downloads and direct arbitrary command/options are not accepted.

One browser capture runs at a time. A login wall or CAPTCHA changes the persisted run to `manual_action_required` and leaves its exact page open in the persistent context. The operator completes the action through loopback-only noVNC, then explicitly resumes the same job. Each attempt writes a numbered challenge screenshot; successful completion writes bounded HTML and a final screenshot. The manifest, screenshot and HTML receive independent SHA-256 hashes, and capture/resume/failure transitions receive investigation audit events. The application never mounts or reads the profile volume and never receives credentials. The agent can maintain multiple validated named persistent sock identities; switching closes the active context and reopens only the selected profile, and profile switching/backup/restore are blocked while a capture is active. Encrypted profile backup uses an Argon2id-derived key with libsodium SecretBox authenticated encryption. Restore authenticates the payload before extraction, rejects links/devices/path traversal and never records the password. For Instaloader and Maigret only, the token-authenticated agent can export a hardcoded, domain-filtered cookie subset into application memory. The app passes that subset to exactly one isolated runner; the runner validates the scope again, creates a private temporary cookie file, removes it after execution and never returns its contents. No other collector receives browser state.

The browser supplies only a validated query, enum query type, selected tool IDs, bounded timeouts and a named preconfigured proxy. It cannot supply executable names or options. For external CLI collectors, the application adapter constructs the command and the private runner checks the executable, option allowlist, output path and disabled features again. Application-side third-party HTTP(S) egress uses the shared `app/services/egress_policy.py` boundary: schemes and credential-bearing URLs are rejected, DNS answers are required to be globally routable and the validated address is pinned for the connection, redirects are disabled, configured or per-run proxies are selected explicitly, a bounded User-Agent is supplied, and response bodies are consumed through streamed byte limits. Internal Corvus service traffic such as the runner, browser agent, SearXNG and Metasearch2 stays on its private Docker network and is deliberately outside this public-egress policy. The built-in Bing and SearXNG name adapters are deliberate exceptions to the generic runner protocol: neither accepts a user-supplied destination. Bing contacts only the fixed HTTPS RSS endpoint through the shared egress boundary, follows no redirect and enforces response, URL and relevance limits. SearXNG contacts only the fixed private `http://searxng:8080` service on the Docker backend network and applies the same public-result and relevance boundaries before persisting a finding.

Each tool service has a non-root UID, read-only root filesystem, dropped capabilities, `no-new-privileges`, memory/CPU limits, no published port, no Docker socket, a private backend network and a separate egress network. Output is limited to per-job tmpfs and is returned to the orchestrator. Tool failures are stored on independent `ToolRun` rows.

The orchestrator creates `raw/<investigation>/<run>/process-output.txt` before execution and appends sanitised, timestamped stdout/stderr lines as they arrive. On normal completion it writes a canonical separated stdout/stderr snapshot before parsing results. Startup recovery appends an interruption marker to any partial log before marking a stale running `ToolRun` failed, so an application restart no longer destroys the last collector diagnostics. The execution-log viewer accepts only investigation and run identifiers, verifies ownership, reconstructs that fixed path beneath the configured evidence root, rejects symlink/path escape, applies a 5 MiB limit and serves escaped text or a plain-text download. It never accepts a browser-supplied filesystem path and never substitutes another run's log. JSON artifacts remain a separate run-scoped evidence surface because many upstream tools produce diagnostic text without producing JSON.

Profile-class findings from username investigations are keyed first by normalised platform plus searched username so human-profile and API aliases merge into one account record; the preferred human-facing URL is retained. Other findings fall back to canonical URL, platform plus normalised identifier, then source identifier. A duplicate row accumulates `source_tools` and metadata provenance entries containing tool, source record and raw reference. Display-name similarity never merges accounts and no identity assertion is created.

Account existence is evaluated separately from finding or identity-linkage confidence. A bounded verifier checks up to 250 profile claims per pass, prioritising low-confidence technical leads. Authoritative platform APIs, exact rich collector objects, HTTP 404/410 and explicit soft-404 content may resolve existence; blocked, rate-limited, generic or JavaScript-shell responses remain unresolved. Verification metadata records an existence state and existence confidence independently. A confirmed missing account becomes `not_found` with zero finding confidence rather than receiving a misleading high positive score. Completed investigations can rerun this verifier without rerunning collectors, and the shared summary exposes checked claims versus the total profile-claim set.

Email-to-username pivots remain inside the same investigation, but each follow-up `ToolRun` carries its own query value/type, source finding, depth and automatic/manual origin. Candidate extraction accepts only explicit username, login, handle, screen-name or non-numeric account-ID fields from found/likely email findings; URLs, email addresses, arbitrary finding values, platform names and numeric IDs are rejected. At most five distinct usernames are followed, each once and only to depth one. Restarting a completed investigation executes only newly queued runs, so its original email tools are never repeated accidentally.

The presentation layer derives read-only projections from persisted runs, findings, profile metadata, image state, location observations and analyst correlation decisions. Dashboard cards, the case console, JSON export and HTML report consume the shared investigation summary so totals cannot drift between surfaces. Username investigations additionally derive a unified account projection on demand: same-platform/account records are merged, complementary source metadata is retained, grouped names/usernames/IDs/locations/images are extracted, and explicit dated fields become semantically labelled account events. No second account database or timeline table is introduced. Source-specific metadata created during duplicate reconciliation preserves the collector responsible for each field or event, while stable finding and tool-run IDs link every projection item back to the technical register. The browser report preview and downloadable HTML use the same self-contained branded template. JSON schema 1.3 and the report include the unified account assessment and timeline alongside the cover, executive overview, positive findings, separated existence/identity confidence, platform/location coverage, collector/browser provenance, complete technical register, notes and limitations. Preview-only print/navigation controls load from a local script and are omitted from the downloaded artifact; no external font, image or script is required.

The Investigation Graph is another read-only projection of that same persisted evidence, not a graph database. Stable entity and relationship IDs are derived from investigation, finding and evidence identifiers. Subject, username, email, profile, image, domain, document, location, archive, account-event and collector nodes are joined only by explicit stored relationships such as the searched identifier, collector provenance, public links, extracted public-email observations, possible usernames derived from email evidence, parsed account dates, archive observations, location observations and retained account/image/face correlation decisions. Analyst node notes and manual relationships are stored separately under a case-scoped application-setting key, audited, and projected back into graph JSON as analyst interpretation rather than source evidence. Account-event nodes are bounded, omit dates explicitly marked ambiguous, and retain their timestamp, source field, extractor and semantic-confidence metadata. Email addresses and email-derived possible usernames are marked prominent so they remain visible in the concise overview. Candidate, rejected, contradicted, observed and confirmed states remain distinct in graph JSON and visual line patterns; a prominent candidate identifier remains labelled as a hypothesis even when its visibility relationship is rendered as an observation. External graph links are reconstructed through a credential-free public HTTP(S) boundary and local/private literal hosts are omitted. Identifier nodes expose only case-bound collection actions for validated username/email/domain values; the confirmation route lists compatible fixed adapters and duplicate queued/runs are suppressed.

The graph UI is a local JavaScript/SVG asset served by FastAPI under the existing content-security policy. It provides deterministic subject-centred, entity-grouped, provenance-flow and chronological account-event layouts, pan/zoom, drag and keyboard movement, filters, include-selected-only isolation, reversible per-session exclusion, provenance inspection and local PNG/JSON export. Applying the chronological layout enables event nodes, orders them by parsed time and places linked account nodes above the event axis; it changes presentation only. Every control, node and relationship exposes hover/focus help. Profile nodes use bundled local platform marks with deterministic initials as fallback; no favicon request leaves the workstation. The default overview suppresses single-source low-confidence findings and derivative event/image/domain/archive nodes while retaining verified, corroborated, rich high-confidence, location, email and email-derived username evidence. The analyst can reveal the complete projection explicitly through **All findings** or the dedicated event control; nothing is removed from graph JSON or case evidence. Manual exclusions and include-only state are ephemeral. Node coordinates are presentation state only: a bounded map of known node IDs is stored under a case-scoped `application_settings` key after CSRF validation, emits save/reset audit events and is removed when the investigation is deleted. Layout and visibility operations cannot mutate findings, correlations or source evidence.

The manual search workbench only targets allowlisted Google and Bing search endpoints. Core packs and reusable templates are rendered from validated fields, analyst-selected engines/platforms/document types and optional bounded dates. Full-name investigations queue both built-in name adapters. Bing executes five fixed RSS query groups, retaining at most ten records per group with raw XML. SearXNG executes the same five groups against a private self-hosted service, retains bounded per-query JSON and records every unresponsive upstream engine. Both reject irrelevant/private/internal results and create deduplicated `likely` findings with title, snippet and query lineage. Duplicate canonical URLs merge without losing source/query provenance. SearXNG enables the keyless Bing, Brave web-search and Mwmbl engines that passed live engine-by-engine acceptance; it has no paid API or account configuration. Upstream engine identity is retained on every result so SearXNG evidence can be distinguished from the direct Bing RSS collector. The case opens on the normal investigation page; dedicated exact-name, identity-context, document, social, review and fitness query packs remain available for deeper manual work. Dynamic manual queries are carried in HMAC-signed tokens bound to the investigation; the browser cannot substitute another query or redirect host without invalidating the signature. Reusable templates are persisted locally in `search_templates` and support only documented placeholders without attribute/index access or arbitrary format operations.

Search-result import remains an explicit analyst action separate from the bounded Bing RSS collector. A batch accepts at most 50 public HTTP(S) URLs from URL lines, tab-separated records or JSON, rejects local/private and credential-bearing destinations, strips common tracking parameters and creates a completed synthetic `search_import` run. New results are stored as `likely` analyst-selected leads. A matching canonical URL adds capped provenance and the `search_import` source to the existing finding instead of increasing the evidence count.

Location evidence is persisted separately from flat finding metadata in `location_observations`. Each row retains the place hierarchy, optional coordinates and precision radius, evidence type, occurred/published/first-observed/last-observed dates, source platform and URL, account identifier, privacy-mask state, confidence and raw analyst evidence. Existing profile-declared locations are promoted into this register at low confidence. Duplicate source observations update their last-observed timestamp instead of adding false support.

The unauthenticated location collector is intentionally narrower than the future managed-browser boundary. It accepts only allowlisted review and fitness hosts, resolves them to public addresses before retrieval, optionally enforces robots.txt, blocks redirects and authentication walls, and accepts bounded HTML only. Evidence is imported only from schema.org/JSON-LD or explicit geo metadata; arbitrary prose is not converted into a location. Claimed review visit dates remain separate from publication dates, and visible route privacy warnings increase the stored precision radius rather than being reverse-engineered.

Location clusters are derived presentation objects, not new facts. They group normalised place labels and classify support as single, repeated, recurring or corroborated according to observation and independent-platform counts. These labels deliberately avoid claiming residence or physical presence. Future map and habitual-area analysis must incorporate coordinate precision, temporal overlap, privacy masks and minimum independent-source thresholds.

SSE delivers queued/running/final states, sanitised lines, rate limits and completion. When a collector enters a terminal state, the browser performs one coalesced, no-store refresh of the persisted findings table, case metrics and unified account projection, rebinds local evidence controls and reapplies the analyst's current filters. This updates account cards, grouped fields and timeline events as runs finish without reloading the whole page or treating transient SSE payloads as the source of truth. Cancellation marks the investigation, sends DELETE to active runners and terminates process groups. Startup changes stale running jobs to structured `interrupted` failures only after appending an interruption marker to their partial execution logs; finished data and last-received process output survive restarts.

`browser_runs` is a separate provenance register linked to an investigation. It stores the requested/final URL, collector and session labels, run/challenge state, timestamps, Chromium version, local artifact references and hashes. Artifact references are resolved beneath the read-only evidence root before use; only PNG screenshots are served to the UI, while raw HTML and manifests remain in the local evidence volume. Portable evidence bundles are generated separately from source storage: an analyst can select findings and redact identifiers, notes or external URLs, then export structured case JSON plus optional bounded raw artifacts and a SHA-256 manifest. Bundle generation never mutates the persisted investigation.

SQLite WAL is suitable for the intended single local deployment. `OSINT_MAX_CONCURRENT_INVESTIGATIONS`, the global `OSINT_MAX_CONCURRENT_COLLECTORS` semaphore and adapter-level limits bound concurrency. The default global collector limit is three, preventing every broad username engine from saturating a workstation simultaneously while preserving independent tool timeouts. Holehe is fixed at one concurrent run. Proxy selection is explicit; there is no rotation, CAPTCHA bypass or evasion logic.

Specialist enrichment is separated from default discovery at the adapter contract. An adapter may declare `default_selected = False`; it remains visible and manually selectable for compatible investigations but is excluded from automatic default tool selection. This boundary is used for DuckDuckGo Instant Answer, GLEIF, Irish CRO Open Data, optional Companies House, Gravatar, GitHub discovery, GitHub Developer Identity, Federated Identity Resolver, Microsoft Entra Tenant Metadata, OpenPGP, optional authorised-feed OpenPhish correlation, Telegram public-page collection, AlienVault OTX historical URLs, URLScan historical search, Live Site Intelligence and Domain RDAP. GitHub Developer Identity samples only a bounded set of a selected public account's owned repositories, commits and public signing keys; commit names/emails and key fingerprints are correlation evidence rather than automatic ownership conclusions. Federated Identity accepts only exact WebFinger/ActivityPub or Matrix identifiers and retrieves public discovery/profile metadata without following, joining, messaging or authenticating. Microsoft Entra Tenant Metadata accepts an analyst-selected domain and stops at tenant-specific public OpenID/federation metadata; it never submits a username or initiates an authentication flow. CRO searches only the official daily Open Data snapshot and does not infer director relationships that source does not expose. Companies House is registered only when an examiner stores an API key and bounds company, officer and appointment retrieval. Retained-artifact analysis is an in-process zero-egress action over the case's existing `raw/<investigation>` tree, while RIPEstat/ARIN infrastructure enrichment accepts only analyst-supplied public IP/ASN resources; a configured AbuseIPDB key adds an explicit IP-only 90-day reputation lookup with no report submission or verbose reporter-comment collection. Historical URL discovery is likewise passive and source-specific: Common Crawl, AlienVault OTX and optional URLScan observations become ordinary `historical_url` findings with source/date provenance, while automatic Wayback metadata is projected into the same case-level Historical URLs view. URLScan is registered only when an operator configures an API key, performs Search API requests only, never submits a new scan, and never writes the key into case evidence, logs or audit details. OpenPhish is likewise absent until an examiner configures an authorised OpenPhish-hosted feed; the Community feed is not a default organisational data source, and case evidence retains only matches plus feed hash/timestamp rather than the licensed feed or secret access URL.

VAT and video enrichment are explicit case actions rather than new investigation types. VIES submits only an examiner-supplied EU/Northern Ireland VAT number to the European Commission validation service and stores the official response. Public video metadata extraction accepts only an analyst-supplied URL on a small allowlist of video-capable platforms and executes pinned yt-dlp in its own hardened runner with `--skip-download --dump-single-json --no-playlist`; only a bounded metadata allowlist is retained, not media payloads or format/download manifests.

Live Site Intelligence is intentionally not a generic spider or vulnerability scanner. For an explicitly selected domain case it performs bounded public GET retrieval only, honours `robots.txt`, seeds from at most three in-domain sitemaps, refuses to crawl outbound domains, and caps page count, traversal depth, JavaScript count, per-response size and total bytes. It does not submit forms, mutate parameters, fuzz paths, attempt authentication or extract high-entropy secrets. Public emails, document/social/outbound links, JavaScript endpoint strings, tracking identifiers and declared generator/server/powered-by hints retain the source page/script that exposed them. When a fetched same-domain JavaScript asset explicitly declares a source map through a response header or `sourceMappingURL`, the collector may retrieve that map under separate byte/map/source caps; it never guesses map filenames. Source-map extraction is limited to declared source paths, public repository/package references, developer identifiers and same-domain endpoint strings, with internal-looking values treated as leads rather than live infrastructure. Tracking identifiers are correlation leads only. Domain registration uses a separate manual-only RDAP adapter: IANA's bootstrap registry selects the authoritative HTTPS service for the TLD, then one bounded domain lookup retains public status/events/entities/nameservers without a legacy WHOIS subprocess.

Telegram uses two default-safe evidence boundaries. Public handles may be collected only through the explicit bounded HTTPS `t.me` adapter; Telegram Desktop JSON exports are parsed offline, retained by SHA-256 and projected into normal findings, case timeline and graph entities/relationships. Imported sender IDs, username/email/phone strings, URLs, media references and reply relationships remain source-backed evidence, not ownership assertions. No third-party Telegram bot or invasive extension is called automatically, and authenticated MTProto/session collection is not hidden behind ordinary username or phone searches.

Discord import follows the same offline, zero-egress shape as Telegram, over two source formats rather than one. `app/services/discord_intelligence.py` parses an analyst-supplied DiscordChatExporter JSON export or a discrawl-compatible SQLite archive — both validated against the field/table shapes read directly from each upstream's own source (see `THIRD_PARTY_NOTICES.md`), not guessed from sample output. Snowflake IDs are decoded entirely offline into creation timestamps (no lookup, no network access, no third-party service). Messages, senders, mentions, reply relationships, attachments and extracted username/email/phone/URL strings are projected into the same finding, timeline and graph model as Telegram, with an explicit `discord_import_source` provenance field distinguishing which format produced each record. Neither import path contacts Discord.

The optional phone-presence collector checks Snapchat and explicitly enabled Amazon flows. Its separate routing option uses the configured Tor sidecar, when available.

Internet Archive operations are separate from tool-container execution. Automatic CDX discovery checks at most ten eligible positive/likely findings and retains at most 50 digest-distinct capture records per URL, including the first and latest observation rendered in cases/reports. Archived-page comparison fetches bounded HTML without executing scripts, and Save Page Now is an explicit CSRF-protected analyst action. Save submissions accept only public HTTP(S) URLs, reject local/private targets and embedded credentials, do not follow redirects, retain no response body, and write structured success or failure metadata to the local audit trail. Archive timestamps are observations, not asserted page-creation dates.

Identity Evolution consumes digest-distinct CDX captures for one original URL and samples at most 25 evenly across the available period. Each selected HTML capture is parsed into a dated observation; archived avatar assets remain behind the hardened local image-cache boundary and are compared using SHA-256 plus 64-bit perceptual dHash. The analyst view separates source observations from derived changes and does not assert that similarly named accounts belong to the same person.
